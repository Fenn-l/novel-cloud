## 3. 版本 C｜详细版（带亮点分点，适合校招 / 1-3 年 / 技术面为主）

```
项目名称：novel-cloud 微服务小说门户
项目周期：[ ]        角色：[ ]        团队规模：[个人 / 人]
项目描述：[同版本 B 项目描述]
技术栈：[同版本 B 技术栈]

核心职责：
· 负责服务拆分与公共能力建设：抽取 novel-common（统一响应、JWT、ThreadLocal
  用户上下文、消息体）与 novel-config（缓存/锁/异常/XSS 横切配置），8 个服务复用；
  网关按 URL 前缀路由，内部接口走 Feign 直连。
· 负责小说核心域（书/章节/正文/评论）的接口设计与实现，共 14 张业务表；
  设计「发布章节」写链路：分布式锁 → 本地事务三表写 → 清缓存 → 事务提交后发 MQ。
· 负责缓存、消息、搜索、并发四条技术主线的方案设计与问题修复。

项目亮点 / 难点：
【缓存一致性】本地缓存多实例下，共享队列是 competing consumer，一条失效消息
  只会被一个实例消费，其余实例脏数据要等 TTL。改为 fanout + 每实例 AnonymousQueue
  独占队列实现广播清理；并刻意不为该消费者加共享幂等键，避免退化成单实例执行。
【消息可靠性】事务提交后发送避免「消息已发、DB 回滚」；publisher confirm +
  失败待重放列表覆盖「DB 已提交、消息没发出」；消费端 msgId 幂等且在失败时
  删除幂等键以允许死信重放；DLQ 落 Redis 留痕；XXL-JOB 全量同步做最终兜底。
【并发控制】锁粒度按业务维度设计（SpEL 动态 key），锁切面用 @Order 置于事务外层
  保证 unlock 发生在 commit 之后；DB 唯一键作为最后防线，DuplicateKeyException
  由全局异常处理器转成明确业务错误。
【检索】function_score 用 log1p 压缩热度避免大值碾压文本相关性；search_after
  采用 [_score desc, id asc] 稳定排序，游标模式下忽略用户排序避免翻页错乱。

工程治理：主动下线「配置写了但没生效」的 ShardingSphere 分表与 Spring Boot
  Admin，删除 22 个零调用遗留实体/Mapper 与纯示例消费者，把 MQ 拓扑从公共包
  拆到各消费服务，使依赖 MQ 的服务从 8 个降到 2 个；修复 NPE、越界、
  目录穿越、缓存注解失效等 30+ 处缺陷，并补齐核心业务代码注释。
```

## 8. 自我介绍口播稿

### 60 秒版

> 我最近在做的一个项目是 novel-cloud，一个基于 Spring Cloud Alibaba 的微服务小说门户，8 个服务、48 个接口。
> 业务主线是注册登录、找书、读章节、发评论，以及作家发布作品和章节。
> 我重点做了三件事：一是 Caffeine + Redis 两级缓存扛读流量，二是用 RabbitMQ 把发布章节后的 ES 索引更新和多实例缓存失效做成事件广播，三是用 Redisson 锁保护两处先查后写的并发竞态。
> 另外我对工程做了一轮收敛，把配了但没生效的分库分表、监控中心、死代码都砍掉了，因为我觉得简历上的技术点必须能讲清取舍，否则被追问反而扣分。

### 3 分钟版（按「背景 → 主线 → 三个亮点 → 边界」展开）

> 项目背景：这是基于开源 novel 的微服务版做二次开发，按业务域拆成网关 + 7 个业务服务，共 48 个接口、14 张主链路表。
>
> 最核心的一条链路是作家发布章节：作家端请求经 author 服务校验身份后，Feign 转到 book 服务，先加 Redisson 锁（粒度到 bookId），开启本地事务写章节、正文、回写书籍汇总，清本实例缓存，事务提交后发 MQ 广播；search 服务增量更新 ES，book 服务每个实例清各自本地缓存。
>
> 这条链路上我处理了几个比较典型的问题：
> 第一，消息必须在 afterCommit 发，否则事务回滚 ES 会有脏数据；反过来「提交成功但消息没发出」用 publisher confirm + 待重放列表 + XXL-JOB 全量兜底。这里我坦白没有本地消息表，是轻量近似。
> 第二，本地缓存是多实例各一份，共享队列是竞争消费，只有一个实例会收到失效消息，所以我改成 fanout + 每实例独占队列广播，并且这个消费者不能加共享幂等键，否则又退化成单实例。
> 第三，锁切面必须在事务外层，否则 unlock 早于 commit，并发请求会读到旧章节号；DB 唯一键是最后一道兜底。
>
> 缓存方面按体积和共享需求分层：正文这种大文本放 Redis，书籍/章节/榜单放本地；点击量走 SQL 原子自增并接受 TTL 内最终一致，避免高频写把缓存打穿。搜索用 ES 的 function_score 做热度加权、search_after 做深分页，全量靠 XXL-JOB、增量靠 MQ。
>
> 最后说下边界：付费阅读、订阅扣费、书架增删、阅读历史、评论回复都没实现，相关表是单体版遗留；网关也不做鉴权，认证在各服务拦截器。这些我主动列清楚，不把它们算作已做的功能。

## 9. 排版与投递建议

- **项目名后面别加「（个人项目）」以外的修饰**；如果是课程/自学，写「个人项目」即可，别写「企业级生产系统」。
- **技术栈单独一行**，方便 HR 关键词检索；不要把技术栈塞进描述长句里。
- **亮点用「问题 → 方案 → 结果/代价」句式**，比「使用了 XX」有说服力。
- **篇幅**：1 年以内经验，项目经历控制在 250~350 字；3 年以上可展开到 500 字并加 2 条量化/治理成果。
- **一定要准备「最难的问题」**：面试官常问「这个项目里你遇到的最难的问题是什么」。推荐答「本地缓存多实例失效」或「锁与事务的顺序」，因为这两个能连讲 5 分钟并且有明确对错。
- **务必自己跑一遍**：`start-all.ps1` + `doc/es/book.http`，能说出「我实际验证过发布章节后 ES 文档和详情页最新章都变了」，可信度完全不同。

## 10. 一句话收尾

> 简历上真正加分的不是「用了多少中间件」，而是**每个词背后都有一条能讲清取舍、也敢说边界的链路**。
