## 1. 微服务拆分与治理

### 考点 1.1 拆分依据
按**业务域 + 数据归属**拆：每个服务持有自己的表，共同依赖 `novel-core` 的横切能力；`search` 单独拆因为数据源是 ES 而非 MySQL，伸缩与发布节奏不同。
> 主动补：这是学习项目，服务粒度偏细；生产里 `news/resource/home` 完全可合并，拆太细会放大分布式复杂度。

### 考点 1.2 服务间调用
OpenFeign + Nacos `lb://服务名`。内部接口 `/api/inner/**` 不经过网关，由 Feign 直连。

| 坑 | 状态 | 说明 / 答法 |
|---|---|---|
| `/api/inner/**` 内网裸奔 | **[坦白]** | 端口在局域网可达、无服务间认证。生产应加网络隔离 / mTLS / 内部令牌 |
| Feign 无超时与重试配置 | **[坦白]** | 用默认超时，生产应按接口设 `connectTimeout/readTimeout` |
| fallback 返回空导致上游 NPE | **[已修]** | 评论列表 `listNewestComments` 对 `userInfoMap.get()` 判空，降级时用「匿名用户」兜底——**降级不该把故障转移到上游** |
| 逐条远程调用 N+1 | **[已修]** | 一次 `listUserInfoByIds(ids)` 批量查 + 内存 Map join；`toMap` 加合并函数防重复 key 抛异常 |
| `toMap` 遇重复 id 抛异常 | **[已修]** | 加 `(a,b) -> a` 合并函数 |
| Feign 参数漏 `@RequestBody` | **[坦白]** | 部分 POST 复杂对象未统一加注解，序列化行为不一致，属已知不一致点 |
| `feign.sentinel.enabled=true` 但没有规则 | **[坦白]** | 只让 fallback 在抛异常时生效，不是完整熔断。别把这句配置说成「做了 Sentinel 限流」 |

### 考点 1.3 网关
网关只做 8 条 URL 前缀路由 + 白名单 CORS，**不鉴权、不限流**。认证散落在各服务拦截器里（见第 2 节）。
> 答法：好处是服务直连不依赖网关、改造成本低；坏处是每个服务重复实现、策略难统一。生产更推荐网关统一解析 JWT 并透传 userId，同时做网络隔离。

## 2. 认证与安全

### 链路真相
`JwtUtils`（HS256、7 天、`systemKeyHeader=front`）→ `UserHolder`（两个静态 ThreadLocal）→ Controller。`afterCompletion` 里 `clear()` 防线程复用串号。

| 服务 | 拦截器 | 行为 |
|---|---|---|
| user | `AuthInterceptor` | 解析 JWT → 查 `userInfoCache` 确认用户存在 → `setUserId`；放行 register/login |
| author | `AuthInterceptor` | 同上 + 查 `authorInfoCache` 确认作家身份 → `setAuthorId` |
| book | `TokenParseInterceptor` | **只挂 `/content/*`**，只解析、不校验、不报错 |

### 坑清单

| 坑 | 状态 | 答法 |
|---|---|---|

## 3. 缓存（Caffeine + Redis）★ 最容易连环追问

### 先背这张分层表

| 缓存 | 介质 | TTL | 为什么这么放 |
|---|---|---|---|
| 分类列表 | Caffeine | 常驻 | 几乎不变，本地零网络开销 |
| 书信息 / 章节元信息 | Caffeine | 18h / 6h | 读多写少，进程内最快 |
| 榜单（点击/新书/更新） | Redis 6h / Caffeine 30min / 60s | 分散 | 避免同时失效，点击榜跨实例共享 |
| 章节正文 | **Redis** | 12h | 大文本，不能在每个 JVM 堆里各存一份 |
| 用户 / 作家信息 | **Redis** | 24h / 48h | 登录后跨服务、跨实例要读同一份 |
| 首页推荐位 | Caffeine | 24h | 运营配置的固定推荐位 |
| 友情链接 | Redis | 24h | 原为 0（永不失效），已改 |

`CacheConsts.CacheEnum` 用 `type`（0 本地 / 1 双写 / 2 远程）+ `ttl` + `maxSize` 声明式驱动 `CacheConfig` 创建两套 `CacheManager`，Caffeine 那个标 `@Primary`。

### 坑清单（重点，逐个能展开讲）

**坑 3.1 本地缓存多实例失效 —— 本次优化的核心亮点** **[已修]**
- 现象：共享持久队列是 **competing consumer**，一条「清缓存」消息只会被某一个实例取走，其余实例的 Caffeine 一直脏到 18h TTL 过期。
- 修法：fanout 交换机 + 每个 book 实例一个 `AnonymousQueue`（非持久 / exclusive / autoDelete），一条消息复制投递到所有实例，各清各的（`BookCacheAmqpConfig` + `BookChangeCacheListener`）。
- 加分点：这个消费者**刻意不做 msgId 幂等去重**——共享 Redis 幂等键会让它退化成「只有第一个实例执行」。清缓存本身幂等，重复无害；实例下线队列自动删除，不堆积。
- 替代方案对比：Redis Pub/Sub（更轻但无持久化、订阅者掉线即丢）、引入广播中间件、或干脆把这类缓存全放 Redis（牺牲本地缓存性能）。

**坑 3.2 `@CacheEvict` 清不掉作家缓存** **[已修]**
`evictAuthorCache()` 既不指定 key 也不 `allEntries`，默认 key 是 `SimpleKey.EMPTY`，而 `getAuthor` 的 key 是 `userId` → 注册成作家后仍查不到身份。已加 `allEntries = true`。

**坑 3.3 自调用让 `@CachePut` 完全失效** **[已修]**
`getBookInfo()`（`@Cacheable`）内部 `this.cachePutBookInfo(id)` 是同类自调用，**没走 Spring 代理**，`@CachePut` 永远不触发。已把查询逻辑内联进 `getBookInfo()`。
> 延伸：所有 Spring AOP 注解（`@Transactional` / `@Cacheable` / `@Async` / 自定义切面）都怕自调用，解决方式是拆类、注入自身代理或用 `AopContext.currentProxy()`。

**坑 3.4 空结果被缓存 24 小时** **[已修]**
Feign 降级或首页无数据时返回空列表，被 `@Cacheable` 缓存一整天；原来 Service 里「结果为空就 evictCache」只能救**下一次**请求，本次用户仍看到空页。现在在 `HomeBookCacheManager` 加 `unless = "#result == null or #result.isEmpty()"`，并删掉 Service 里那段反直觉逻辑。

**坑 3.5 点击量与缓存不一致** **[已修·取舍]**
`addVisitCount` 走 SQL 原子自增，**刻意不失效** `bookInfoCache`：详情页每次浏览都 +1，每次清缓存等于让读多写少的接口全部回源 DB。点击量是展示型指标，允许 TTL 内滞后；要求精确的点击榜由独立 Redis 榜单按周期重算。
> 面试要说这是**明确的最终一致取舍**，不是没发现。更高量级应改成 Redis 计数器 + 批量合并回 DB。

**坑 3.6 友情链接 `ttl=0` 且无失效入口** **[已修]**
改成 24h，并补 `evictFriendLinkCache(allEntries=true)`（暂无后台调用方，属预留运维入口）。

**坑 3.7 缓存穿透 / 击穿 / 雪崩** **[部分坦白]**
- 穿透：靠参数校验 + `unless` 不缓存空值；**没有布隆过滤器**，是可补的点。
- 击穿：热点 key 过期瞬间的并发回源**没有互斥重建**（`sync=true` 或分布式锁），已知短板。
- 雪崩：TTL 分散（60s ~ 48h）+ 本地/远程两层，不会同时大面积失效。

**坑 3.8 首页推荐 `bookInfoMap.get()` NPE** **[已修]**
Feign 少返回某本书时原来直接 `.getBookName()` NPE，现在过滤掉无详情的推荐项。

## 4. RabbitMQ ★ 第二大主战场

### 拓扑（背下来）

```
saveBookChapter ──(事务 afterCommit)──> EXCHANGE-BOOK-CHANGE (fanout)
   ├─ QUEUE-ES-BOOK-UPDATE  → search 服务 → 回查 DB → 增量更新 ES
   │      └─ 失败 → DLX → QUEUE-BOOK-CHANGE-DLQ → 写 Redis 留痕(200 条)
   └─ QUEUE-BOOK-CACHE-BROADCAST-{uuid}  → book 服务每实例独占 → 清本地 Caffeine

生产端 confirm 未确认 → Redis 列表 book:mq:send:failed（待重放）
XXL-JOB 全量同步 → 最终兜底
```

### 可靠性五层（从前往后讲）

| 层 | 做法 | 挡住什么 |
|---|---|---|
| 1 | `TransactionSynchronization.afterCommit` 才发 | 事务回滚但消息已发，ES 索引到不存在的数据 |
| 2 | `publisher-confirm-type: correlated` + `mandatory` / returns | 事务已提交但 broker 没收到 / 消息无法路由到队列 |
| 3 | ConfirmCallback 把失败 payload 写 `book:mq:send:failed` | 事务不可回滚，只能留痕等补偿重放 |
| 4 | 消费端 `setIfAbsent(msgId)` 幂等，**失败时删除幂等键** | 重复投递；也避免死信重放被误判为重复 |
| 5 | DLX → DLQ → 写 `book:mq:dlq:records` | 失败消息不再「只打一行日志就消失」 |
| 兜底 | XXL-JOB `saveToEsJobHandler` 全量重建 | 增量链路整体故障 |

### 坑清单

| 坑 | 状态 | 答法 |
|---|---|---|
| 早期 ES 消费者 `target == null` 时 `warn + return` | **[已修]** | 消息被 ack、索引静默漏更新。现在一律抛异常进死信留痕 |
| 幂等键在业务前写入、失败不删除 | **[已修]** | 死信在 10 分钟内重放会被误判为重复跳过。ES 消费者 catch 里必须 `delete(dedupKey)` |
| DLQ 只打日志，消息 ack 后彻底消失 | **[已修]** | 现在写 Redis 保留 200 条；但**仍没有自动重放** |
| 公共包的 `AmqpConfig` 被 8 个服务全扫描 | **[已修]** | 启动类统一 `scanBasePackages="io.github.xxyopen.novel"`，公共包里的 Queue/Exchange/`@EnableRabbit` 让 home/news/author/resource 也强依赖 MQ（旧日志每服务约 33 次 `AmqpConnectException`）。改成「谁消费谁声明」：`BookCacheAmqpConfig`(book) + `BookEsAmqpConfig`(search)，只剩 2 个服务依赖 MQ |
| Fanout 下还传 `routingKey="book.change"` | **[已修]** | fanout 忽略 routingKey，固定传空串 |
| 第三个「书架通知」消费者 | **[已修·删除]** | 类注释自认"示例"，写入的列表无真实下游，纯装饰 |
| 没有本地消息表（Outbox） | **[坦白]** | confirm 只能保证 broker 收到，不能保证消费成功。本项目用「Redis 待重放 + 全量同步」近似；极端情况（连写 Redis 也失败）仍可能丢。生产应把业务数据与待发消息同事务落库，再由投递任务扫描发送 + 告警 |
| DLQ 无自动重放、无重试上限、无告警 | **[坦白]** | 生产要补定时任务 + 次数阈值 + 报警 |
| 消息只带 ID 不带业务字段 | **[设计]** | 消费时回查 DB 当前值，**天然免疫乱序与延迟**；代价是多一次 Feign 调用 |
| 缓存消费者为什么不做幂等 | **[设计]** | 见坑 3.1，广播场景下共享幂等键会退化成单实例执行 |

### 常被追问的三个「为什么」
- **为什么 afterCommit**：先发再提交，事务回滚时 ES 已索引脏数据。
- **为什么 fanout 而不是 direct/topic**：一次变更要让**多个不同职责的下游各自处理**，不需要按条件路由；fanout 忽略 routingKey 正好。
- **confirm / return / mandatory 区别**：confirm 管「broker 有没有收到」，return 管「收到了但路由不到队列」，`mandatory=true` 才会把不可路由消息退回给生产者。

## 5. Elasticsearch 与数据同步

### 考点速记
- **mapping**：`doc/es/book.http` 手工执行，17 个字段；`bookName/authorName/bookDesc` 为 text，其余 long/integer/short/keyword。优化时补齐了 `isVip`、`commentCount`（旧索引需重建）。
- **查询**：`bool` 过滤（`word_count>0`、keyword、方向、分类、isVip、bookStatus、字数区间、更新时间）+ `multi_match`（书名^3/作者^2/简介^1）+ `function_score` + 高亮。
- **`function_score`**：`最终得分 = 文本相关度 × (1 + 0.5·log1p(点击量) + 0.1·log1p(字数))`。`log1p` 压缩量级防止热门书碾压相关性；`boostMode=Multiply` 让热度只是放大而非取代相关度；`missing(0.0)` 兼容老文档。系数是经验值，需 A/B 数据调。
- **分页**：普通 `from+size`；深分页 `search_after`，排序强制稳定为 `[_score desc, id asc]`，游标模式下**刻意忽略用户传的 sort**（游标是在另一套排序下生成的会翻页错乱）。代价：只能「加载更多」，不能跳页。
- **同步**：XXL-JOB 全量（按自增 ID 游标分批 30 条，`word_count>0`）+ MQ 增量；`book.http` 与全量任务是 ES 的最终兜底。

### 坑清单

| 坑 | 状态 | 答法 |
|---|---|---|
| 索引不自动创建，报 `index_not_found_exception` | **[坦白]** | 必须手工执行 `doc/es/book.http`；生产应由启动检查/迁移脚本建索引 |
| ES 挂了无降级 | **[坦白]** | 全局异常处理器返回系统错误，**没有回退到 MySQL like 查询**。写链路不受影响（消息进 DLQ），但搜索不可用 |
| `isVip` / `bookStatus` 是 DTO 里的死字段 | **[已修]** | 现已真正参与 `bool` 过滤，并补齐 mapping |
| 分页参数无边界，`pageNum=0` 算出负数 from | **[已修]** | 归一化到 1、pageSize 上限 50 |
| `hit.highlight()` / `total` 可能为 null | **[已修]** | 判空后使用 |
| `searchAfter` 游标格式非法导致 500 | **[已修]** | 校验分数与 ID 两段，并在游标模式忽略 sort |
| `lastChapterUpdateTime` 为 null 导致全量同步整批 NPE | **[已修]** | 新书该列允许 null，转 0L |
| ES Java Client 8.2 连的是 ES 7.x | **[坦白]** | 版本与 README 声明不一致，属环境事实；生产应统一版本 |
| `sort` 只支持单字段、忽略排序方向 | **[坦白]** | 当前实现简化，多字段排序需扩展 |

## 6. 并发与 Redisson 分布式锁 ★

### 只用在两处「先查后写」
`saveComment`（锁粒度 userId×bookId）、`saveBookChapter`（锁粒度 bookId）。

| 设计点 | 说明 |
|---|---|
| 锁 key | `Lock::prefix::<SpEL 求值>`，`@Key(expr="#{bookId}")` 以 DTO 为根对象，精确到业务维度 |
| 快速失败 | `isWait=false` → 无参 `tryLock()`，拿不到立即抛业务异常。低频写，并发主因是用户连点，排队只会拖住线程 |
| 错误码 | `failCode` 默认值原来是 `ErrorCodeEnum.OK` → 抢锁失败返回「code=00000 成功但没数据」，已改 `USER_REQ_MANY` |
| 释放 | `finally` 里先 `isHeldByCurrentThread()` 再 unlock，防止超时自动释放后误放别人的锁 |
| 切面顺序 | `LockAspect` 标 `@Order(HIGHEST_PRECEDENCE)`，**必须在事务切面外层** |
| 兜底 | DB 唯一键 `uk_bookId_chapterNum`、`uk_bookId_userId` + `DuplicateKeyException` 全局转换 |

### 坑 6.1 锁与事务的顺序（最容易答错）**[已修]**
若事务切面在外、锁切面在内，`unlock()` 会发生在事务 **commit 之前**：锁释放了但数据还没提交，另一个请求拿到锁后读到旧的最大章节号，又算出同一个号。把锁切面提到最外层，`joinPoint.proceed()` 返回时内层事务已提交，才释放锁。

### 坑 6.2 发章节原本没锁 **[已修]**
章节号 = `max(chapter_num)+1`，并发请求算出同一个号，撞唯一键后一个 500。现在加 `@Lock(prefix="publishChapter")` + `@Key(expr="#{bookId}")`。

### 常问
- **为什么用 Redisson 不用 SETNX**：可重入、看门狗自动续期、解锁校验持有者、统一 API；手写要自己用 Lua 保证「判断+删除」原子并解决续期。
- **看门狗是什么**：未显式指定 leaseTime 时，Redisson 后台定时续期，避免业务没跑完锁就过期；锁超时后 `isHeldByCurrentThread()` 会返回 false，跳过 unlock。
- **锁失效了怎么办**：DB 唯一键是最后防线，异常由 `CommonExceptionHandler` 转成明确业务错误，不会变成笼统 500。

| 坑 | 状态 | 答法 |
|---|---|---|
| 全项目只有 1 处 `@Transactional` | **[设计·坦白]** | 就是 `saveBookChapter`。其余多为单表写入，靠自动提交 + 唯一键；注册「查重→插入」无事务，靠 `uk_username` 兜底 |

## 9. 「为什么砍掉 ShardingSphere」标准答案

> 原本想演示 `book_content` 按 `chapter_id % 10` 分 10 张表，但：
> ① `doc/sql/init.sql` 只建了 `book_content` 一张表，没有 `book_content0..9`，配置注释却写「已创建」——DDL 与规则对不上，开箱即坏；
> ② 同时配了 `spring.datasource` 和 `spring.shardingsphere.datasource.ds_0`，两套 Hikari 配置并存；
> ③ 运行日志里 0 条 `Logic SQL / Actual SQL`，只出现一个 `HikariPool-1`，`sql-show: true` 也没打出分片日志 → **配了但没生效**。
>
> 与其留一个被追问「分片键怎么路由、跨分片怎么分页、怎么扩容」就答不上来的摆设，不如下线。
> 真要做正文分表，分片键应该选 **`book_id`**（同一本书的章节尽量落同一片，避免目录查询跨片合并），而不是 `chapter_id`；还要解决跨分片分页、分布式 ID、扩容迁移。

同理下线 `novel-monitor`：与业务主线无关，且 Nacos 地址写死 `192.168.10.110`、内存弱口令 `user/password`、pom 插件重复声明。各服务保留 actuator 的 health/info/metrics，需要大盘时再单独接。

## 12. 连环追问模拟（面试官顺着一条链路连问）

> 场景：你说「我用 MQ 做发布章节后的异步解耦」，接下来可能被连问 8 层。

1. **消息什么时候发？** → 事务 `afterCommit` 之后。
2. **为什么不是事务里发？** → 事务回滚会产生「ES 有、DB 没有」的脏数据。
3. **那提交成功但发送失败呢？** → publisher confirm 检测 → 写 `book:mq:send:failed` 待重放 → XXL-JOB 全量兜底。
4. **confirm 就够了吗？** → 不够，它只保证 broker 收到；本项目**没有本地消息表**，极端情况仍可能丢，这是坦白的简化。
5. **消息重复了怎么办？** → ES 消费者按 msgId `setIfAbsent` 幂等，失败删键允许重放。
6. **消息乱序/延迟呢？** → 消息只带 bookId，消费时回查 DB 当前值，天然免疫。
7. **消费失败怎么办？** → `default-requeue-rejected=false` + DLX → DLQ → 写 Redis 留痕；**没有自动重放**，生产要补。
8. **为什么清缓存那个消费者不做幂等？** → 广播场景下共享幂等键会退化成单实例执行；清缓存本身幂等。（再追）**为什么用独占队列？** → 共享持久队列是 competing consumer，只有一个实例收到，其它实例本地缓存会脏到 TTL 过期。

> 能答到第 8 层，这条链路就稳了。

另一组高频连环：**缓存** → 分层依据 → 一致性 → 多实例广播 → 为什么不去重 → 点击量取舍 → 穿透击穿雪崩 → 更高 QPS 怎么改。

## 14. 主动坦白的短板（说得出来 = 有工程判断）

1. 没有本地消息表（Outbox），极端情况仍可能丢消息；DLQ 无自动重放与告警。
2. ES 无降级、索引需手工建；mapping 变更要重建索引 + 重跑全量。
3. 缓存击穿没做互斥重建、没有布隆过滤器；没有压测数据。
4. 网关无鉴权无限流，`/api/inner/**` 内网接口零保护。
5. JWT 无刷新/吊销、密钥硬编码；密码 MD5 固定盐；验证码可爆破。
6. 公共 yml 明文口令；三套环境的账号/库名不一致。
7. Feign 无超时与重试配置、部分参数注解不统一。
8. 无单元测试 / 集成测试 / CI。

> 收尾话术：**「这些是我明确知道没做的，按优先级我会先补 X，因为……」** ——比被问出来强得多。
